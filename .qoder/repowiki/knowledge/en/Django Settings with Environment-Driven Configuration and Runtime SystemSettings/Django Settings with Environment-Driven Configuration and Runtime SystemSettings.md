## Overview

The Market Rental System uses a standard Django project configuration layered over environment variables and a database-backed runtime settings model. There is no dedicated `config/` package, YAML, or TOML config loader — all configuration lives in `market_rental/settings.py`, supplemented by `.env.example` and the `SystemSetting` model.

## How configuration is loaded

1. **Startup**: `market_rental/settings.py` calls `dotenv.load_dotenv(BASE_DIR / ".env")` (line 11), loading key/value pairs from `.env` into `os.environ`. The file is git-ignored; `.env.example` documents every supported variable.
2. **Environment precedence**: Every setting reads via `os.environ.get(...)`, so real process environment variables always override `.env` values. Production deployments (Vercel) supply secrets through the platform's env var UI rather than files.
3. **Database selection** (priority order):
   - If `DATABASE_URL` is set → `dj_database_url.config(...)` parses it (supports MySQL, PostgreSQL, etc.). This is the production path.
   - Else if `DB_ENGINE == "mysql"` → connects to local XAMPP MySQL/MariaDB using `MYSQL_DB`, `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD` (defaults match stock XAMPP: root, empty password).
   - Else → SQLite at `BASE_DIR / "db.sqlite3"` (zero-config local dev).
4. **Local DB bootstrap**: When using MySQL locally, `_ensure_mysql_database()` attempts to `CREATE DATABASE IF NOT EXISTS` before Django's migrate runs, swallowing connection errors so the app can still start if the server is unavailable.
5. **Security toggles**: `DEBUG` is parsed from `DJANGO_DEBUG` as a boolean (`{"1", "true", "yes", "on"}`). `SECRET_KEY` falls back to a development-only value when unset. `ALLOWED_HOSTS` is split from `DJANGO_ALLOWED_HOSTS`; non-debug mode auto-appends `.vercel.app`, `localhost`, `127.0.0.1`. CSRF trusted origins accept `https://*.vercel.app` plus any comma-separated list from `DJANGO_CSRF_TRUSTED_ORIGINS`.
6. **Static assets**: In production (`not DEBUG`) WhiteNoise serves hashed static files via `CompressedManifestStaticFilesStorage`; dev keeps plain filenames and uses a `?v={{ STATIC_VERSION }}` querystring generated by the `static_version` context processor.

## Runtime application settings (database-backed)

Operational business configuration is not hard-coded but persisted in the `core.models.SystemSetting` model:

| Field | Purpose |
|---|---|
| `municipality_name`, `market_name`, `office_name` | Identity branding |
| `receipt_prefix` | Receipt numbering prefix |
| `default_due_day` | Default billing due day |
| `penalty_type` (`fixed` / `percentage`) | Penalty calculation mode |
| `penalty_value` | Penalty amount or rate |
| `grace_period` | Days before penalties apply |
| `logo` | Uploaded market logo |
| `theme_color` | Brand color (hex) |
| `terms_and_conditions` | Contract boilerplate, one clause per line |

`SystemSetting.objects.first()` is fetched once per request by the `core.context_processors.system_settings` template context processor and exposed as `system_settings` in templates. A default contract terms string (`DEFAULT_CONTRACT_TERMS`) is seeded on the model class so the first record has sensible defaults.

## Template-level configuration exposure

Three context processors registered in `TEMPLATES[0]["OPTIONS"]["context_processors"]` expose configuration to every template:

- `core.context_processors.system_settings` — runtime `SystemSetting` instance.
- `core.context_processors.user_roles` — current user role, `is_collector`, and `can_manage_records` flags derived from `UserProfile.role` and `MANAGEMENT_ROLES`.
- `core.context_processors.static_version` — mtime of `static/css/output.css` for cache-busting URLs.

## Conventions and constraints observed

- All sensitive values (`DJANGO_SECRET_KEY`, `DATABASE_URL`, MySQL credentials) are read exclusively from `os.environ`; no secret is committed to source control.
- `.env` is intentionally git-ignored (documented in `.env.example` header comments); only `.env.example` is tracked.
- Local development is zero-config: leaving `DATABASE_URL` unset and `DB_ENGINE=sqlite` gives a working SQLite backend out of the box.
- Production overrides take precedence: `DATABASE_URL` wins over `DB_ENGINE`; real process env vars win over `.env`.
- Vercel-specific defaults are baked in: `.vercel.app` host acceptance, `https://*.vercel.app` CSRF trusted origin, and `SECURE_PROXY_SSL_HEADER` for reverse-proxy SSL termination.
- Database engine switching is explicit via the `DB_ENGINE` env var (`sqlite` or `mysql`); there is no dynamic import or plugin mechanism beyond these two paths.
- Business policy (penalties, grace period, branding, terms) is treated as mutable runtime data stored in `SystemSetting`, not as code constants — administrators change them through the admin interface without redeploying.
- Static asset versioning is dual-mode: hashed manifests in production (WhiteNoise `CompressedManifestStaticFilesStorage`) and mtime-based querystrings in development.
